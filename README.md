# РБПО — лабораторная работа №3

**Вариант 27. Редакция новостного издания**

Java 21 · Spring Boot 3.5.5 · Spring Data JPA · PostgreSQL 16 · Flyway · Maven

## Назначение приложения

Проект продолжает REST API из лабораторной работы №2. Предметная область и пять основных сущностей сохранены, но хранение в оперативной памяти заменено реляционной базой данных PostgreSQL. Все прежние CRUD-маршруты `/api/...` продолжают работать.

Приложение позволяет управлять рубриками новостного издания, пользователями, статьями, редакторскими проверками и выпусками. Кроме CRUD, реализован редакционный процесс: отправка материала на проверку, решение редактора, возврат на доработку, включение одобренного материала в выпуск и публикация выпуска.

## Сущности и таблицы

| Сущность | Таблица | Основные поля |
|---|---|---|
| Рубрика (`EditorialSection`) | `editorial_sections` | `id`, `name`, `publication_available` |
| Пользователь (`User`) | `app_users` | `id`, `username`, `display_name`, `email` |
| Статья (`Article`) | `articles` | `id`, `section_id`, `author_id`, `title`, `article_text`, `status` |
| Редакторская проверка (`EditorialReview`) | `editorial_reviews` | `id`, `article_id`, `decision`, `remarks`, `reviewed_at` |
| Выпуск издания (`EditionIssue`) | `edition_issues` | `id`, `issue_date`, `status` |
| Связь выпуска со статьёй | `edition_issue_articles` | `issue_id`, `article_id`, `article_position` |

`edition_issue_articles` — таблица связи многие-ко-многим между выпусками и статьями. Она нужна, поскольку один выпуск содержит несколько статей, а статья может находиться в черновых выпусках до публикации.

## Связи и ограничения целостности

- Одна рубрика содержит много статей. Каждая статья принадлежит ровно одной рубрике.
- Один пользователь может быть автором многих статей. У каждой статьи ровно один автор.
- У статьи может быть несколько редакторских проверок. Каждая проверка относится к одной статье.
- Выпуски и статьи связаны отношением многие-ко-многим через `edition_issue_articles`.
- `section_id`, `author_id`, `article_id`, `issue_id` защищены внешними ключами.
- Удаление рубрики или пользователя каскадно удаляет принадлежащие им статьи, проверки этих статей и строки связей с выпусками, если среди этих статей нет опубликованных материалов.
- Удаление неопубликованной статьи удаляет её проверки и связи со всеми выпусками. Выпуск при этом сохраняется.
- Опубликованную статью и опубликованный выпуск удалить нельзя. Также нельзя удалить автора или рубрику, если за ними закреплены опубликованные статьи. Это предотвращает потерю опубликованной истории и появление пустых опубликованных выпусков.
- `username`, `email` и название рубрики уникальны. Email может отсутствовать.
- Для названий, текста, логина, статусов и решений заданы ограничения `NOT NULL`, `CHECK` и длины столбцов.
- Дублирование статьи внутри одного выпуска блокируется составным первичным ключом таблицы связей.
- Решение и статья в записи редакторской проверки неизменяемы через PATCH; редактировать можно замечания. Новая запись проверки должна соответствовать текущему статусу статьи. Активную запись одобрения опубликованного или одобренного материала удалить нельзя.
- Позиция статьи в выпуске не может быть отрицательной.
- Публикация статьи запрещена, если у её рубрики `publication_available = false`.

Схема создаётся и обновляется миграциями Flyway в `src/main/resources/db/migration`. Демонстрационные записи добавляются миграцией `V2` и остаются в PostgreSQL после перезапуска приложения.

## Бизнес-операции

| № | Операция | Маршрут | Правило и изменение состояния |
|---|---|---|---|
| 1 | Отправить статью на редакторскую проверку | `POST /api/business-operations/articles/{articleId}/submit-for-review` | Только `DRAFT`; статья переходит в `IN_REVIEW`. |
| 2 | Одобрить статью | `POST /api/business-operations/articles/{articleId}/approve` | Только `IN_REVIEW`; статья становится `APPROVED`, создаётся проверка `APPROVED` с серверным временем. |
| 3 | Вернуть статью на доработку | `POST /api/business-operations/articles/{articleId}/request-revision` | Только `IN_REVIEW`; статья возвращается в `DRAFT`, создаётся проверка `NEEDS_REVISION`. |
| 4 | Включить статью в выпуск | `POST /api/business-operations/issues/{issueId}/articles/{articleId}` | Только для чернового выпуска; статья должна быть `APPROVED`; дубли запрещены. |
| 5 | Опубликовать выпуск | `POST /api/business-operations/issues/{issueId}/publish` | Выпуск должен быть черновым и непустым; все статьи должны быть одобрены, их рубрики должны разрешать публикацию; статьи и выпуск переводятся в `PUBLISHED` одной транзакцией. Опубликованные статьи автоматически удаляются из других черновых выпусков. |

Операции 2 и 3 одновременно изменяют статью и добавляют запись редакторской проверки. Операция 4 меняет состав выпуска, операция 5 согласованно меняет состояние выпуска и связанных статей. Проверки выполняются внутри транзакций; конкурентное изменение статьи или выпуска ограничено пессимистической блокировкой строки.

Повторное выполнение операции в неподходящем состоянии возвращает `409 Conflict`. Например, нельзя одобрить черновик, добавить черновую статью в выпуск или опубликовать пустой выпуск. CRUD не подменяет бизнес-операции: создание выпуска со статусом `PUBLISHED` и прямое изменение статуса выпуска на `PUBLISHED` через PATCH запрещены. Для сохранения истории опубликованные статьи и выпуски, а также авторы и рубрики опубликованных материалов защищены от удаления.

## Безопасность доступа к БД

В Docker Compose создаются две отдельные учётные записи:

- `POSTGRES_USER` — административная учётная запись PostgreSQL, используемая только при первоначальной инициализации контейнера;
- `APP_DB_USERNAME` — прикладная роль, под которой работает Spring Boot.

Прикладная роль создаётся скриптом `db/init/10-create-app-user.sh` с атрибутами `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`. Она получает подключение к одной БД и права `USAGE, CREATE` в схеме `public`, необходимые для миграций Flyway и работы приложения. Пароли задаются через `.env`, файл `.env` исключён из Git. В репозитории хранится только шаблон `.env.example`.

Значения в `.env.example` предназначены только для локального демонстрационного запуска. Перед использованием в общей или удалённой среде замени оба пароля на собственные сложные значения и не отправляй `.env` в Git. Скрипт создания роли выполняется только при первой инициализации тома PostgreSQL. Если после этого изменить имя или пароль прикладной роли в `.env`, потребуется отдельно обновить роль в БД; удаление тома через `docker compose down -v` приведёт к потере всех данных.

## Структура проекта

- `controller` — REST-контроллеры лабораторной №2 и контроллер бизнес-операций;
- `service` — правила предметной области, проверки ссылок и транзакционные сценарии;
- `repository` — Spring Data JPA репозитории для PostgreSQL;
- `model` — JPA-сущности и перечисления статусов;
- `dto` — входные запросы и результат редакторского решения;
- `exception` — единый JSON-формат ошибок API;
- `config` — системные часы приложения;
- `src/main/resources/db/migration` — SQL-миграции и тестовые записи;
- `db/init` — создание отдельной ограниченной роли БД;
- `postman` — коллекция CRUD- и бизнес-запросов.

## Запуск через Docker Compose

Требуются Docker Desktop и Docker Compose.

1. В корне проекта создай `.env` из шаблона:

   ```powershell
   Copy-Item .env.example .env
   ```

2. При необходимости измени пароли в `.env`.
3. Собери и запусти PostgreSQL и REST API:

   ```powershell
   docker compose up --build -d
   ```

4. Посмотри состояние контейнеров:

   ```powershell
   docker compose ps
   ```

5. Посмотри логи приложения:

   ```powershell
   docker compose logs -f api
   ```

API доступен по адресу `http://localhost:8080`. После первого старта Flyway создаст таблицы и наполнит их тестовыми записями. Проверить работу можно запросом `GET http://localhost:8080/api/articles`.

Остановить контейнеры без удаления базы:

```powershell
docker compose down
```

Полностью удалить контейнеры и демонстрационную БД вместе с данными:

```powershell
docker compose down -v
```

Последняя команда удаляет том PostgreSQL. Используй её только если данные можно стереть.

## Запуск из IntelliJ IDEA

1. Скопируй `.env.example` в `.env`.
2. Запусти только PostgreSQL: `docker compose up -d db`.
3. Открой `pom.xml` в IntelliJ IDEA и дождись импорта Maven.
4. Запусти `RbpoLab3Application`.

Приложение прочитает `DB_URL`, `DB_USERNAME` и `DB_PASSWORD` из `.env`. Если запускаешь не через Docker, PostgreSQL должен быть доступен по адресу из `DB_URL`.

## Коллекция Postman

Импортируй `postman/RBPO_Lab3_Variant27.postman_collection.json` в Postman. У коллекции есть переменная `baseUrl`, по умолчанию `http://localhost:8080`. Запускай запросы сверху вниз: сначала CRUD-сценарии, затем бизнес-операции. Скрипты коллекции сохраняют созданные идентификаторы, поэтому вручную подставлять ID между запросами не требуется. Коллекция использует фиксированные тестовые имена и рассчитана на запуск на чистой демонстрационной базе. Для полного повторного прогона с нуля можно выполнить `docker compose down -v`, затем снова `docker compose up --build -d`; первая команда удаляет все данные PostgreSQL.

Коллекция содержит `GET` списка, `GET` по ID, `POST`, `PATCH` и `DELETE` для каждой из пяти сущностей, а также все пять новых бизнес-операций. Для бизнес-процесса создаются черновой материал, материал для возврата на доработку и черновой выпуск.

## Тестирование

Тесты `RbpoLab3IntegrationTest` запускают приложение с тестовой БД H2 в режиме совместимости с PostgreSQL. Это не заменяет проверку на реальном PostgreSQL, но позволяет автоматически проверить HTTP-контракты и бизнес-логику без запущенного Docker.

Запуск:

```powershell
mvn clean test
```

Тесты проверяют:

- CRUD всех пяти сущностей;
- серверное заполнение `reviewedAt`;
- переходы статьи между статусами;
- создание проверок при одобрении и возврате на доработку;
- включение статьи в выпуск и публикацию выпуска;
- отклонение недопустимых переходов;
- каскадное удаление автора или рубрики, статей и проверок с очисткой связей выпуска;
- сохранение состава выпуска при PATCH только даты и очистку других черновых выпусков от уже опубликованной статьи;
- запрет удаления опубликованной статьи, выпуска, автора и рубрики.
